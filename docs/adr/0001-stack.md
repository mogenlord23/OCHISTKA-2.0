# ADR 0001: стек и слои платформы

- **Дата:** 2026-11-17
- **Статус:** принято

## Контекст

OCHISTKA — утилита обслуживания компьютера. Текущий этап — Windows 10/11 x64. Позже нужны macOS и Linux без переписывания интерфейса и ядра. Приложению нужны десктопное окно, доступ к системным сведениям и операциям, а также небольшой установщик.

## Решение: стек

- **Tauri 2** — оболочка приложения. Интерфейс работает в системном WebView (WebView2 на Windows, есть в Windows 11), установщик получается небольшим, связь с ядром идёт через типизированные команды Tauri.
- **Rust** — ядро и системные операции. Безопасность памяти, один язык для адаптеров по ОС, зрелые библиотеки (например, sysinfo для чтения сведений о системе).
- **Svelte 5 + TypeScript** — интерфейс. Небольшой рантайм, руны для состояния, статическая проверка типов.
- **Vite** — сборка и сервер разработки; Tauri использует его по умолчанию.

Не используем: WPF. Старый код WPF остаётся справкой по поведению и не копируется.

## Решение: слои платформы

1. **Оболочка и интерфейс:** Tauri 2, Svelte 5 (руны), TypeScript, Vite.
2. **Ядро:** Rust, workspace из трёх крейтов:
   - `crates/ochistka-core` — DTO, расчёты и порт `SystemInfoPort`; без кода ОС;
   - `crates/platform` — адаптеры по ОС за портом; `windows/` содержит реализацию, `macos/` и `linux/` — заглушки, возвращающие `Unsupported`;
   - `apps/desktop/src-tauri` — Tauri-команды и управляющее состояние.
3. **Системные сведения:** библиотека sysinfo внутри адаптера Windows. Только чтение.
4. **Граница интерфейса:** интерфейс обращается к системе только через типизированные Tauri-команды; обёртка `api.ts` — единственная точка вызова.
5. **Типы фронтенда:** сначала писались вручную (см. дополнение 2026-11-18: теперь генерируются из DTO ядра).
6. **Внешние команды:** на этапе 1 не запускаем. Все системные вызовы — чтение через sysinfo.

## Последствия

- Сборка на Windows требует MSVC Build Tools с рабочей нагрузкой C++ и WebView2.
- Переход на macOS или Linux заменяет заглушку в своём модуле; интерфейс и ядро не меняются.
- Ручные типы фронтенда могли разойтись с DTO; с 2026-11-18 типы генерируются (см. дополнение ниже).
- sysinfo определяет поведение чтения на Windows; для каждого нового показателя нужно отдельно проверить его на Windows.
- Проверки качества: `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, `svelte-check`, `vitest`, Prettier.

## Дополнение 2026-11-18: типы фронтенда генерируются

- Решение владельца (D5): TypeScript-типы генерируются из Rust DTO крейтом `ts-rs` (12.x, derive `TS` с `#[ts(export, export_to = "...")]`; camelCase берётся из `#[serde(rename_all)]`). Рукописные копии удалены; `apps/desktop/src/lib/types.ts` реэкспортирует `apps/desktop/src/lib/generated/*.ts`.
- Файлы в `generated/` коммитятся и не правятся вручную. Тест `crates/ochistka-core/tests/generated_types.rs` в `cargo test` экспортирует типы во временную папку и сравнивает с закоммиченными; при расхождении тест падает. Обновление: `OCHISTKA_BLESS=1 cargo test -p ochistka-core --test generated_types`.
- `u64` (байты) отображается в `number` через `#[ts(type = "number")]`, а не в `bigint`: JSON из Tauri отдаёт число, а значение точно до 2^53−1 байт (около 8 ПиБ), чего хватает для объёмов дисков и памяти. Если появится поле, которое может превысить это значение, его нужно передавать строкой.
- `api.ts` проверяет форму ответов `get_system_overview`, `scan_start`, `clamav_status` во время выполнения, потому что `invoke<T>` только приводит тип.
