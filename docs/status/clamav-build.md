## Исследование протокола переноса (2026-11-23)

- План до реализации: открыть источник без ссылок относительно закреплённых каталогов, сверить устройство, ID, размер и SHA-256 с находкой; выполнить перенос только при наличии доказанного атомарного способа связать действие с проверенным объектом. До подтверждения такой операции разрешена только проверка без изменений диска.
- На Linux `openat2` с `RESOLVE_NO_SYMLINKS` ограничивает разрешение путей, а `renameat2` с `RENAME_NOREPLACE` запрещает замену назначения, но переименование выбирает источник по имени, а не по ранее открытому дескриптору. Подмена имени между проверкой и вызовом остаётся возможной. Создание жёсткой ссылки из дескриптора не решает атомарное удаление исходного имени: `unlinkat` тоже работает по имени, которое могло быть заменено. Откат по имени может натолкнуться на занятый путь. Поэтому эти шаги без дополнительных гарантий о каталоге не удовлетворяют требованию сохранять каждый исходный объект.
- Проверка перед действием не даёт гарантии для последующего действия. Межтомное копирование с последующим удалением имеет ту же проблему и не реализуется как безопасный fallback. Создание и сохранение манифеста после аварии также требует отдельно проверенного протокола восстановления.
- Windows: необходимо изучить проверку reparse points и file ID и переименование по handle без замены на целевых файловых системах; macOS: отдельно изучить file ID и семантику `renameatx_np` с запретом замены. Ни их атомарность относительно открытого источника, ни обработка аварии пока не подтверждены проверками этих ОС.

## Модель угроз и проект восстановления (2026-11-23)

Для всех ОС предполагается конкурирующий процесс с правами пользователя, способный изменить файл, заменить имя или родительский каталог; процессы с повышенными правами и недоверенные сетевые серверы могут обладать ещё большими возможностями. Открытый файловый объект сохраняет привязку к объекту, но не запрещает его изменение и не удерживает имя каталога. ID и хеш — данные для сравнения, не замок. Кооперативные блокировки не останавливают нарушителя, который их игнорирует. Права каталога следует проверять вместе с ACL и фактической моделью доверия; каталог того же пользователя не является автоматически защищённым от других его процессов.

- **Linux:** дескрипторы директорий позволяют закрепить выбранные каталоги, `openat2` может запретить ссылки, а `renameat2(RENAME_NOREPLACE)` — перезапись назначения на поддерживаемой ФС. Никакая из этих мер отдельно не связывает вызов переименования имени с ранее проверенным открытым файлом. Жёсткая ссылка не решает гонку удаления исходного имени. Возможный ограниченный режим потребовал бы доказать исключительный контроль каталога и содержимого на всём интервале, включая процессы того же пользователя; сейчас такой контроль не обеспечивается.
- **Windows:** нужны проверки handle и file ID, reparse points на каждом шаге, ACL и режима совместного доступа, затем отдельное подтверждение семантики операции переименования по handle и запрета замены на целевой ФС. Открытый handle и отказ в совместном доступе не считаются защитой от всех привилегированных процессов и удалённого сервера. Реализация и проверка — planned.
- **macOS:** нужны отдельные проверки file ID, директорий и ссылок, механизма no-replace и блокировок; операции с именем не считаются связанными с ранее открытым объектом. Поведение APFS и других ФС требует проверки на macOS. Реализация и проверка — planned.
- Сетевые, съёмные, пользовательские и другие ФС с неподтверждёнными семантикой no-replace, синхронизацией и восстановлением после аварии должны получать отказ. Не утверждается поддержка конкретной ФС на какой-либо ОС до её проверки. Межтомный перенос также не поддержан.

Ниже — **требования к будущему журналируемому протоколу, а не реализованный или доказанный алгоритм**. `S` — исходная запись, `T` — временный объект карантина, `Q` — конечный объект, `J` — журнал/манифест; каждое принятие решения требует сверки идентичности и проверенных гарантий ФС.

| Переход | Требуемое состояние после ошибки или аварии |
| --- | --- |
| Проверка S и открытие handle | S не меняется; T и Q не создаются; J прежний. Открытый handle не переживает перезапуск. |
| Подготовка намерения | J должен содержать устойчивую запись идентичности и путей; до подтверждённой записи S нельзя изменять. При ошибке записи прежний J сохраняется. |
| Создание T/Q без перезаписи | При коллизии, нехватке места или ошибке создания S и существующий Q сохраняются. После аварии журнал должен позволять отличить свои T/Q от чужих объектов. |
| Проверка и синхронизация объекта | До успешной проверки и синхронизации файла и необходимых каталогов S не изменяется; ошибки `fsync` нельзя считать успехом. Повторная проверка не фиксирует неизменность S в будущем. |
| Фиксация записи в J | После атомарной и устойчивой записи J должна оставаться возможность найти и проверить Q. Атомарность обновления, сериализация конкурирующих операций и порядок синхронизации пока не доказаны. |
| Обработка исходного имени | До действия требуется доказанная связь операции именно с проверенным объектом. Если такой связи нет — отказ без удаления S; ни hard link, ни копирование не закрывают эту гонку. |
| Подтверждение операции | Успех допустим лишь после устойчивой записи финального состояния и проверки инвариантов; прерванную операцию следует показывать как незавершённую. |
| Восстановление | Сверить J и Q, создать целевое имя без перезаписи и устойчиво зафиксировать переход. При занятом пути или неопределённости оставить Q и J доступными; защита от подмены здесь тоже требует доказательства. |

Не существует проверенной реализации указанного журнала или процедуры восстановления после перезапуска. До доказательства и тестов по всем фазам UI остаётся в режиме отказа от переноса.
