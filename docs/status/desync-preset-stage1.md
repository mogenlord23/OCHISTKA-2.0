## 6Б.5Г.2Д — умный выбор доступа по каждому сервису (21.11.2026)
- Единый флаг `direct_reachable` заменён независимым состоянием каждого сервиса (Сайты / Discord / Telegram / Игры): `Reachable` / `Unreachable` / `Unchecked`. Неизвестное остаётся «не проверено» и никогда не считается успехом (`routing.rs`).
- Выбор пути для каждого сервиса: прямое соединение → VPN → один цельный Desync-профиль; итог — одно общее решение. Состояние VPN берётся из реального `ConnectionStatus` (`VpnSignal::from_status`): работающий VPN запрещает перехват; непроверенное VPN-подключение блокирует всё; VPN в режиме системного прокси покрывает только сайты, остальные сервисы он не покрывает.
- `DesyncService::plan_access(wanted, observed)` и `start_planned(...)`: запуск движка только по плану. Direct/VPN/Block-планы движок не запускают; повторный запуск не создаёт второй экземпляр; ошибки запуска и нехватка прав не выдаются за успех. Дополнительный запрет в `start_locked` при активном VPN (`VpnRunning`).
- Обратная защита: `VpnService::set_conflict_guard` — VPN не подключается, пока работает перехват (одновременных механизмов нет).
- Реестр подтверждённых покрытий `CONFIRMED_EXTERNAL_PROFILES` по-прежнему пуст: пока нет реального повторяемого опыта на Windows, Desync выбран быть не может. `--dry-run` доказательством не является. Пользовательский переключатель остаётся выключенным.
- Тесты: смешанная доступность, активный/непроверенный VPN, неизвестное состояние, непроверенный профиль, попытка второго запуска, остановка, ошибки запуска/прав, VPN после старта Desync, отказ VPN при работающем перехвате. Локально (Linux): `ochistka-core --lib` 492 ок, `ochistka-platform --lib` 96 ок, fmt ок, clippy core lib чистый. Windows-проверок и сетевых испытаний не было.
- Для следующего подэтапа (безопасная проба полного профиля NetZapret в OCHISTKA): согласие пользователя на реальное сетевое испытание, подключение измерителя доступности по каждому сервису к `ServiceObservations`, привязка `set_conflict_guard` к `DesyncService::is_running` при сборке приложения, запись результата опыта в `CONFIRMED_EXTERNAL_PROFILES` только после повторяемого результата.

## 6Б.5Г.2Е — связка VPN и Desync при запуске приложения (21.11.2026)
- `vpn::build_desync` (Tauri) создаёт один `Arc<DesyncService>` рядом с `Arc<VpnService>`; каталог данных `%LOCALAPPDATA%\OCHISTKA\desync` (`desync_data_dir`). Оба сервиса зарегистрированы через `app.manage`; при старте вызывается `recover_on_start()`.
- Desync получает состояние VPN из настоящего `VpnService::status()` (`vpn_signal_source`), VPN получает защиту `desync_conflict_guard` через `set_conflict_guard`. Связи только через `Weak`: циклов владения нет. Недоступный партнёр = безопасный отказ (VPN считается активным и непроверенным; запуск VPN отклоняется).
- При выходе сначала `DesyncService::shutdown()`, затем `VpnService::shutdown()`.
- Пользовательской команды включения обхода нет; `CONFIRMED_EXTERNAL_PROFILES` пуст; WinDivert не запускался, сетевых испытаний не было.
- **Известное окно гонки:** проверка защиты и сам запуск не атомарны (две раздельные проверки состояния). Перед активацией функции нужен общий атомарный механизм (одна блокировка на оба сервиса). Пока неподтверждённый профиль заблокирован планом.
- Проверено на Linux: `ochistka-core --lib` 493 ок, `cargo check -p ochistka-desktop` ок, fmt ок. На Windows и в запущенном приложении не проверялось.

## 6Б.5Г.2Ж — атомарное право на сетевой режим (21.11.2026)

Линукс: `ochistka-core --lib` 506 ок.
