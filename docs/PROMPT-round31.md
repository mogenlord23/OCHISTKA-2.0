# Круг 31. Проверка компьютера одной кнопкой во вкладке «Вирусы»

## Результат этого круга

Пользователь открывает «Вирусы → Проверка», нажимает **«Проверить компьютер»** и видит ход проверки без выбора папки. Приложение само находит доступные локальные диски. Сначала показывает результаты для важных областей, затем продолжает обход оставшихся допустимых файлов на этих дисках в рамках того же запуска. Пользователь видит, чем проверены файлы, что найдено, что пропущено и закончилась ли проверка. Основной путь приёмки этого круга — Windows 10/11 x64. Общий интерфейс и логика сканирования должны подходить для адаптеров macOS и Linux.

Владелец выбрал «Вирусы» как текущую задачу для чата исполнения. Сетевой этап сохраняет свою очередь. В этом круге работай над сканированием и связанным экраном. Согласуй с планировщиком только реальный блокер, который нельзя снять без чужих правок, недоступной сборки или выбора ветки. Принимай обычные технические решения самостоятельно.

## T1. Установи фактическую базу для правок

- Прочитай `AI/PROJECT_GUIDE.md` («Как начать новую сессию» и «Работа двух чатов и передача заданий»), `AGENTS.md`, раздел «Вирусы» в `CLAUDE.md`, `docs/ai-workflow.md`, относящиеся к антивирусу строки `docs/platform-status.md`, `docs/PROMPT-round30.md` и конец `docs/status/clamav-build.md`. Из `docs/REQUIREMENTS.md` бери только требования к связанному экрану.
- Проверь `git status --short --branch`, `git log -1 --oneline`, ветку и удалённые ссылки. Планировщик подтвердил на GitHub [коммит круга 30](https://github.com/mogenlord23/OCHISTKA-2.0/commit/e5b2a7bf7f162f9b95a52827dd807ef65c9874c6) в `codex/subtabs-hypatia`. На момент подготовки локальный HEAD был тем же, но дерево содержало незакоммиченные изменения в ядре сканирования, сборке платформы, движке признаков и сгенерированных типах. `AGENTS.md` называет рабочей веткой `claude/epic-knuth-0zhg19`. Проверь историю обеих веток. Сохрани правки предыдущего исполнителя. Публикуй только в указанную владельцем ветку после проверки, что нужная база в ней уже есть или перенесена согласованно. Если нужная база есть только на другой ветке и перенос не согласован, верни планировщику точное расхождение и SHA. Без force-push, очистки рабочего дерева и коммитов в `main`.
- Раздели состояния движка по фактам. На зафиксированной базе есть `VirusScanPort`, `ClamAvEngine` и режим «по признакам». В `SuspicionEngine` и состоянии приложения используется `NoModel`. По кругу 29 работала загрузка тестовой базы в платформенных тестах; по кругу 30 у ранее проверенного dev `.exe` не было импорта `libclamav.dll`. Официальный сервер баз на сети владельца отвечал 403. Сначала проверь, закрыли ли эти вопросы более свежие изменения. Если рабочая Windows-сборка всё ещё не содержит движок, устрани адресную причину из круга 30 в согласованной базе, чтобы основной сценарий можно было проверить сквозным тестом. При отсутствии официальных баз покажи честный статус и используй безопасную тестовую базу для приёмки. Доступность официальных баз отрази отдельно.

## T2. Добавь сканирование компьютера через существующий путь

- Начни с `crates/ochistka-core/src/scan.rs`, `crates/platform/src/lib.rs`, `apps/desktop/src-tauri/src/commands.rs` и `apps/desktop/src-tauri/src/lib.rs`. Используй имеющиеся файловые порты, обход, `VirusScanPort`, события прогресса и отмену. Добавь типизированное различие между запуском проверки компьютера и существующим запуском по указанной папке. Сохрани совместимость старых вызовов. Корни для проверки компьютера определяет системный адаптер, а не строка пути из интерфейса.
- Для Windows выбирай доступные локальные фиксированные тома. Документируй охват и исключения. Сетевые и съёмные диски оставь за рамками режима по умолчанию. Не следуй через символические ссылки, junction, reparse points или пути, которые выводят обход за выбранные корни. Предотвращай циклы и повторный обход вложенных приоритетных путей. Проверяй обычные файлы. Ошибки прав, занятые файлы, системные границы и лимиты движка отражай как пропуски или ограничения. Для запуска не требуй повышения прав. При проверке и просмотре результатов не запускай найденные файлы и не отправляй наружу их содержимое или пути.
- Быстрый первый результат обеспечь порядком обхода, а не сокращением охвата. Приоритизируй доступные области вроде загрузок и пользовательских каталогов, после них продолжай по выбранным томам. Не делай отдельный полный предварительный обход ради процента. Ограничь память, конкуренцию и частоту событий. Сохрани отзывчивость интерфейса, остановку между рабочими единицами и запрет двух параллельных сканирований. В отчёте измерь время до первых результатов, полное время и обработанные файлы на воспроизводимом наборе. Укажи ОС, тип диска и размер набора. Произвольного обещания про секунды или проценты ускорения не давай.
- Подпись результата должна соответствовать тому, что сработало. Находки по сигнатуре и находки по признакам различаются. Проверка без доступной базы помечена как проверка по признакам, если этот режим уже доступен. При отмене или существенных пропусках сохраняй статус неполной проверки. «Угроз не найдено» означает только отсутствие находок в проверенных файлах в указанном режиме. Карантин и восстановление остаются отдельными пользовательскими действиями в пределах доказанных гарантий проекта. Ни сканирование, ни будущая оценка ИИ не удаляют файлы и не расширяют текущий карантинный доступ.

## T3. Адаптируй экран и проверь результат

- `apps/desktop/src/components/VirusesPage.svelte`, `apps/desktop/src/lib/scanControl.ts`, `scanState.svelte.ts`, `scanCapabilities.ts` и типизированный клиент команд — основные места проверки. На экране один основной сценарий **«Проверить компьютер»**, при работе — **«Остановить»**. Выбор папки можно сохранить как дополнительное действие, если он уже полезен. Путь, поле ввода и проводник не должны блокировать основной запуск. Переиспользуй текущие карточки, навигацию и дизайн-токены. Покажи фазу, число проверенных файлов, находки и пропуски. Процент отображай только при известном знаменателе. Проверь узкое и обычное окно, клавиатурный фокус, длинные подписи и состояние отмены.
- Добавь адресные проверки, которых не хватает для нового поведения. Покрой запуск без папки, повторное нажатие, отмену, вложенные или пересекающиеся корни, недоступный каталог, отсутствие базы и честную подпись результата. На Windows запусти свежую сборку из корня и пройди сценарий на разрешённых временных данных с безопасным образцом и отдельной тестовой базой. Тестовая настройка должна ограничивать обход временными корнями через существующую тестовую инфраструктуру или подстановку порта. Не добавляй пользовательский обход проверки доступных корней. Для сквозного подтверждения через интерфейс не сканируй личный компьютер владельца без его действия. Если системная защита блокирует EICAR, используй безвредный временный файл с собственной тестовой `.hdb`-сигнатурой в изолированной базе. Не меняй настройки защиты. Убедись, что находка появляется, чистый файл не отмечается, отмена работает, исходные файлы на месте.
- Используй подходящие проверки из `antivirus-checks.yml`. Разделяй PASS/FAIL/NOT RUN для сборки, тестов и реального запуска на Windows, macOS и Linux. Успех общего теста на runner не подтверждает готовность нативного движка или GUI на этой ОС. Проверка с тестовой сигнатурой не заменяет проверку с официальной базой. Если готова публикуемая Windows-сборка, дай ссылку на фактический workflow/артефакт и укажи, что проверено при запуске.

### Команды проверок из корня

Windows PowerShell. Выполняй команды, относящиеся к изменённым частям, и фиксируй итог каждой выбранной проверки.

```powershell
git status --short --branch
git log -1 --oneline
cargo test --locked -p ochistka-core -q scan::tests
cargo test --locked -p ochistka-platform --features libclamav --test virus_scan -q
npm test -w apps/desktop -- src/components/VirusesPage.test.ts src/lib/api.test.ts --reporter=dot
npm run check -w apps/desktop
cargo fmt --all --check
cargo build --locked -p ochistka-desktop
```

Отдельный запуск приложения для проверки на Windows после успешной сборки:

```powershell
npm run dev
```

macOS/Linux Bash, когда доступен соответствующий runner и установлены зависимости проекта:

```bash
cargo test --locked -p ochistka-core -q scan::tests
cargo test --locked -p ochistka-platform --test virus_scan -q
npm test -w apps/desktop -- src/components/VirusesPage.test.ts src/lib/api.test.ts --reporter=dot
```

## Дальнейшие круги для планировщика

1. **Реальный локальный ИИ.** Подключить к существующему `SuspicionModel` компактную версионированную ONNX-модель для поддерживаемых форматов. Проверять источник, лицензию, контрольную сумму и совместимость. Модель использует признаки файла на устройстве и добавляет отдельную объяснимую оценку. Подтвердить путь от извлечения признаков до результата модели, ошибки загрузки, время и память на CPU, а также качество и ложные срабатывания на безопасном воспроизводимом наборе. Чётко разграничить охват сигнатур, эвристик и модели. Подключение рантайма или `NoModel` не закрывает этот круг.
2. **Равная функциональность на настольных ОС.** Подключить и нативно проверить адаптеры macOS и Linux, их системные корни, права, форматы файлов, упаковку движка и модели. Общее ядро переиспользовать, системные команды держать за портами. Зафиксировать статус и результаты по каждой ОС в `docs/platform-status.md`. Под «всеми ОС» здесь понимаются Windows, macOS и Linux для компьютеров.
3. **Замеры и оптимизация на реальных конфигурациях.** Оптимизировать только подтверждённые узкие места и повторно сравнить скорость, пиковую память, качество обнаружения и охват на сопоставимых наборах. Собственная реализация OCHISTKA — это оркестрация проверки, интерфейс, эвристики и интеграция модели с соблюдением лицензий существующих компонентов.

После работы дай фактический результат одной кнопки, изменённые пути, охват и пропуски, режим движка и базы, замеры, PASS/FAIL/NOT RUN по каждой ОС, отдельно статус реального Windows-запуска. Приложи шаги для владельца после опубликованного коммита и SHA. Если публикация не состоялась, не включай `git pull` в инструкцию и назови конкретную причину. Перед передачей обнови релевантный checkpoint и `docs/platform-status.md` по фактам. Один логический Conventional Commit, если завершён круг и согласована ветка. Следующее задание выбирает чат планирования после проверки результата этого круга.
