# Работа с ИИ в OCHISTKA: чаты, память проекта, передача задания

Этот файл описывает рабочий процесс владельца с помощниками. Правила самого проекта
важнее: `AGENTS.md` (Codex и DeepSeek Harness) и `CLAUDE.md` (Claude Code). Если этот
файл расходится с ними, действует `AGENTS.md` и последнее явное решение владельца.

## Память проекта: что читает каждый чат

| Что | Где | Как попадает в чат |
|---|---|---|
| Правила работы | `AGENTS.md`, `CLAUDE.md` | автоматически, в каждом чате |
| Единое руководство | `AI/PROJECT_GUIDE.md` | оба чата, в начале сессии |
| Навыки проекта | `.agents/skills/*/SKILL.md` | DSH и Codex находят сами; вызывать явно (`$ochistka-verify` и т. п.) |
| Состояние и решения | `docs/status/*.md`, `docs/adr/*` | по необходимости, только нужные разделы |
| Текущее задание | `docs/PROMPT-roundN.md` | читает исполнитель |
| План и требования | `docs/PLAN*.md`, `docs/netzapret-plan.md`, `docs/REQUIREMENTS.md` | оба чата, выборочно |

Ничего из этого не нужно пересказывать в чат: помощник читает файлы сам. Поэтому новый
чат не «теряет контекст» — контекст лежит в репозитории и версионируется git.

## Два чата

### 1. «Планирование» — обсуждаем, что делать

- Модель: быстрая и недорогая. Права: **только чтение** (`/permission` → read-only).
- Задача: понять, что хочет владелец, проверить текущее состояние по документам и коду,
  сформулировать ровно один круг работ.
- Результат: файл `docs/PROMPT-roundN.md`. Код не меняется, коммитов нет.

Формат `PROMPT-roundN.md` — по `AI/PROJECT_GUIDE.md` (раздел «Работа двух чатов и передача
заданий»). Обязательный минимум, как в прошлых кругах:

1. Заголовок и одна строка: что меняем.
2. «Общие правила»: ссылки на `AGENTS.md`/`CLAUDE.md`, «не переделывать рабочее»,
   отдельный коммит на этап, честно «implemented / verified на Windows».
3. Этапы `T1…Tn` — по одному помощнику на этап.
4. Требования по номерам: что именно должно быть и как это принимается.
5. Контекст и файлы: что прочитать, где менять, чего не трогать.
6. «Не делать»: что запрещено в этом круге.
7. Как проверять: команды для Windows PowerShell (и macOS/Linux, если применимо),
   отдельно — что считается «проверено на Windows».
8. Формат отчёта: изменённые файлы, PASS / FAIL / NOT RUN по каждой ОС, ветка и commit SHA,
   следующий шаг.

### 2. «Исполнение» — пишем код

- Модель: самая сильная из доступных. Права: запись (danger-full-access — сборке нужен
  доступ к `~/.cargo` и другим путям вне репозитория).
- Задача: взять `docs/PROMPT-roundN.md` и выполнять этапы по одному.
- На каждый этап: правки → целевые тесты → один коммит → пуш в рабочую ветку.
- Отчёт: изменённые пути, PASS / FAIL / NOT RUN, риски, следующий шаг.
- Если задание неоднозначно — вернуть вопрос в чат «Планирование», а не догадываться.

## Git

- Ветка: та, что указана в `AGENTS.md`; `main` не трогаем, force push запрещён.
- Перед работой: `git status`, `git log -1`; чужие непринятые правки не перетираем.
- Один этап — один коммит, сообщение по Conventional Commits (`fix(quarantine): …`).
- Пуш — только после зелёных целевых проверок.
- Токен GitHub лежит в `~/.dsh/.env` (`GITHUB_TOKEN`), в репозитории его нет.
  В песочнице DSH git работает через OpenSSL-бэкенд (`http.sslBackend=openssl`);
  это уже настроено в локальном конфиге репозитория.

## Что делает владелец

1. Открывает чат «Планирование» и обычными словами говорит, что не нравится или что нужно.
2. Читает `docs/PROMPT-roundN.md` — или просит объяснить его простыми словами.
3. Открывает чат «Исполнение» и пишет: «выполняй круг N» (или просто «продолжай»).
4. Смотрит отчёт и проверяет программу на Windows.

## Технические заметки

- DSH работает в локальной копии репозитория (у владельца `B:\Desktop\ochistka-fresh`);
  навыки из `.agents/skills/` подхватываются автоматически, без настройки.
- Команды выполняются через `powershell`; длинные сборки — с ограничением вывода.
- Полный набор тестов, clippy и сборка — только на границе этапа, не в каждом круге
  (см. «Cost-conscious implementation protocol» в `AGENTS.md`).
