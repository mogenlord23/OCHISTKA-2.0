# OCHISTKA 2.0 — единое руководство для ИИ-помощников

Этот файл — общая точка входа для Codex, Claude и других ИИ, работающих с репозиторием. В начале новой сессии прочитай его и актуальные документы состояния, прежде чем предлагать или менять код. Он описывает устойчивые правила проекта. Текущие этапы и результаты проверок бери из документов статуса и Git, а не угадывай по этому файлу.

## Как начать новую сессию

1. Проверь `git status`, текущую ветку и `git log -1`.
2. Прочитай этот файл, затем только связанные с задачей разделы и файлы.
3. Определи из `docs/status/`, актуального плана и истории Git, что уже сделано и что осталось.
4. Сохрани изменения пользователя и предыдущих помощников. Не выполняй reset, force-push, переписывание истории или публикацию в неизвестную ветку.
5. Работай над одной согласованной функциональной задачей за раз. Если задача задана напрямую, принимай обычные технические решения самостоятельно и продолжай.

## Цель и устройство проекта

OCHISTKA 2.0 — приложение для обслуживания компьютера. Оно создаётся для Windows, macOS и Linux. Кроссплатформенность — постоянное требование каждой новой функции и каждого задания для реализации.

- Стек: Tauri 2, Rust, Svelte 5, TypeScript и Vite.
- `apps/desktop` содержит приложение и интерфейс.
- `crates/ochistka-core` содержит независимую от ОС логику и типизированные порты.
- `crates/platform` содержит системные адаптеры Windows, macOS и Linux.
- Интерфейс вызывает системные операции через типизированные Tauri-команды. Системные эффекты не размещай в UI или общем ядре.
- Для каждой ОС реализуй отдельный адаптер, если поведение системно-зависимое. Не оставляй Windows единственной работающей ОС. Не скрывай отсутствие реализации: используй ясное состояние доступности и веди статус отдельно для каждой ОС.
- Семь разделов навигации: VPN, Вирусы, Процессы, Программы, Диски, Компьютер, Оформление. Сверяй актуальный порядок и поведение с текущими решениями проекта.

## Текущие планы и статус

Перед изменениями проверь актуальные документы, относящиеся к задаче:

- `docs/OWNER-REQUESTS.md` — постоянные предпочтения владельца и ограничения. Если они расходятся с этим файлом, следуй более позднему прямому решению владельца; после этого обнови документацию, если расхождение важно для следующих сессий.
- `docs/PLAN.md`, `docs/PLAN-2.md`, `docs/PLAN-3.md` — общий план. Отмеченные пункты могут быть устаревшим scaffolding и не доказывают, что новая функция завершена.
- `docs/platform-status.md` — состояние возможностей по ОС.
- `docs/status/` — проверенные результаты, ограничения и checkpoints.
- `docs/netzapret-plan.md` и checkpoint в `docs/status/` — актуальная работа по Zapret/NetZapret.
- `docs/adr/` — утверждённые архитектурные решения.

Если инструкции расходятся, приоритет имеют последнее явное решение владельца и актуальный checkpoint. Сверяйся с кодом, коммитами и тестами. Отличай `implemented`, `verified`, `planned` и `blocked`. Заглушка не является работающей функцией. Тест на Linux не подтверждает поведение Windows или macOS.

Для работы с Zapret/NetZapret читай актуальный конец `docs/netzapret-plan.md` и самый свежий относящийся к задаче checkpoint. Не возвращай удалённые SonicDPI/WinDivert-компоненты и не создавай новые автономные диагностические архивы вместо работы в приложении. Проверяй происхождение, точную версию, контрольные суммы и лицензии используемых компонентов. Цель владельца — простой единый обход сайтов; не показывай его как готовый и не включай непроверенные сценарии без воспроизводимого подтверждения на целевой ОС и согласия владельца.

## Безопасность и файлы пользователя

- Не удаляй реальные пользовательские файлы необратимо. Очистка и обнаруженные угрозы проходят через карантин с манифестом и возможностью восстановления. Необратимое удаление возможно только отдельным осознанным подтверждением, если такое действие предусмотрено актуальным дизайном.
- Не работай за пределами разрешённых корней и белых списков. Проверяй канонические пути, ссылки, права доступа, file identity, хэши, гонки и частичные сбои с учётом конкретной ОС.
- Не называй операцию безопасной, пока её гарантии не доказаны на целевой ОС. При сомнении откажи без изменения исходного файла и сообщи причину.
- Для антивируса ClamAV, баз сигнатур и ONNX-моделей используй проверенные источники, закреплённые версии, лицензии, TLS и проверку целостности. ИИ работает локально и лишь повышает подозрение. Он не удаляет файлы и не отправляет их содержимое наружу.
- Не запускай и не открывай обнаруженный подозрительный файл. Для тестов используй безопасный EICAR и временные fixture-файлы.
- Не отключай Microsoft Defender, не маскируй драйверы, не меняй firewall, DNS, hosts, proxy или системные настройки без явного разрешения владельца.
- Скачивания выполняй по HTTPS с проверкой подписи или SHA-256 там, где применимо. Не обходи TLS и не меняй ожидаемые контрольные суммы, чтобы заставить операцию пройти.

## Визуальный язык

- Используй существующие дизайн-токены, компоненты и решения, включая `Check.svelte` для флажков и согласованный стиль выбора.
- Сохраняй утверждённый вид приложения и сравнивай визуальные изменения с текущим baseline `f15de11` и релевантными требованиями. Не делай редизайн без запроса.
- Учитывай клавиатуру, доступность, контраст, адаптивность и `prefers-reduced-motion`.
- Не называй визуально проверенным то, что проверено лишь в jsdom или статических CSS-тестах. Указывай размеры окна и ограничения среды.

## Рабочий процесс

- Одна чёткая функциональная цель на этап. Перед изменениями дай короткий план до пяти пунктов.
- Исследуй только необходимые документы и файлы. Используй существующие порты, компоненты и тесты. Не переписывай готовые подсистемы без конкретной причины.
- Пиши или обновляй адресные тесты. Запускай релевантные тесты, сборки, форматтер и проверки типов. Не выдавай непроверенные платформы за успешные.
- По каждой задаче и prompt включай поведение Windows, macOS и Linux, а также фактический статус сборки/проверок для каждой ОС.
- Используй локальные `.agents/skills/` или `.claude/skills/` только по необходимости. Не подключай внешние плагины, MCP или субагентов без явной необходимости и обоснования.
- Общайся с владельцем по-русски и простыми словами. Не требуй от него запускать сложные ручные процедуры, если их может выполнить агент. Для воспроизводимых Windows-проверок подготовь копируемые команды PowerShell.
- Учитывай, что владелец не программист: сам исследуй и выполняй доступную работу, а команды в PowerShell приводи как понятную проверку на его Windows-компьютере после изменения. Не проси его редактировать файлы вручную.
- В конце отчёта перечисли изменённые файлы, PASS / FAIL / NOT RUN, ограничения по каждой ОС, текущую ветку и commit SHA, публикацию и точный следующий шаг.
- Создавай один логический Conventional Commit на завершённый этап и публикуй только в правильную рабочую ветку после проверки истории. Не коммить в `main`, не переписывай историю и не теряй изменения другого помощника.

## Работа двух чатов и передача заданий

Владелец использует отдельные чаты для планирования и реализации. Они работают последовательно, не редактируя репозиторий одновременно. Передавай решения через краткий, но достаточно подробный implementation prompt или статусный документ.

Работай циклом по одной функции:

1. В чате планирования вместе с владельцем обсуди общую цель и составь большой план развития приложения, разбитый на отдельные функции и этапы. Сверь его с актуальным состоянием репозитория и запиши важные решения в подходящий документ проекта.
2. Передавай в чат реализации один этап за раз: подготовь для него конкретный промпт с контекстом, областью изменений и критериями готовности. Не отправляй исполнителю весь общий план как просьбу сделать всё сразу.
3. После реализации изучи отчёт, изменения, результаты проверок и незакрытые ограничения. Уточни или подготовь исправляющий промпт, если функция не соответствует согласованному результату.
4. Заверши проверку функции: релевантные автоматические проверки, визуальные или ручные проверки там, где они нужны, и отдельная оценка Windows, macOS и Linux. Для проверки владельцем приложи подходящие команды PowerShell; команды тестирования и запуска приложения указывай отдельно.
5. Зафиксируй результат и оставшиеся вопросы в плане/checkpoint. Только после этого вместе выберите и спланируйте следующую функцию.

Общий план — это карта очереди, а не просьба реализовать всё сразу. Не перескакивай на следующую функцию, пока текущая не проверена настолько, насколько позволяет доступная среда, а её статус и ограничения не записаны. Если есть блокер, зафиксируй его и обсуди с владельцем следующий безопасный шаг.

Промпт реализации должен содержать цель, актуальный контекст, объём, конкретные файлы для изучения, ограничения, критерии готовности, проверки и формат отчёта. Пиши достаточно полно, чтобы модели не приходилось угадывать, но не повторяй большие файлы и нерелевантную историю. Большой размер prompt сам по себе не экономит лимит.

В конце prompt добавляй команды проверки для Windows PowerShell и macOS/Linux Bash, подходящие именно к изменённым файлам. `git pull --ff-only` включай только когда коммит опубликован в нужной удалённой ветке. Различай команду тестирования и команду запуска приложения.

## Ограничение сессии и checkpoint

Не обещай продолжать работу в фоне после исчерпания лимита или завершения сессии. Если работу нужно будет продолжить, перед остановкой обнови релевантный checkpoint в `docs/status/`: текущая ветка и HEAD, завершённые изменения, тесты с результатами, незавершённые задачи, блокеры и точный следующий шаг. При следующем доступном запуске сначала перечитай checkpoint и проверь Git, затем продолжай без повтора готовой работы.

## Инструкция для новой модели

После чтения этого руководства и актуального checkpoint кратко подтверди, что понял кроссплатформенное требование, текущую ветку/HEAD и ближайший незавершённый этап. Не начинай несвязанную работу. Если пользователь уже дал конкретную задачу, переходи к ней.

Для запуска нового чата владелец может использовать такой короткий текст:

> Сначала прочитай `AI/PROJECT_GUIDE.md` и указанные там актуальные документы владельца и статуса. Проверь ветку, HEAD и незакоммиченные изменения. Кратко подтверди текущее состояние и ближайший этап. Для каждой задачи учитывай Windows, macOS и Linux, честно отмечай, где функция реализована и реально проверена. Затем выполняй мою задачу по правилам руководства.
